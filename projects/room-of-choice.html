抉择的房间

一个循环叙事游戏：你在一间房里醒来，每个选择都在重塑这个房间， 走到结局不算失败——每个结局都是一块拼图。 技术上它是一套配置驱动的叙事引擎： 剧情、线索、结局全部外置，引擎层不认识任何具体节点。

核心决策：把变动源隔离出去

剧情是这类游戏里变动最频繁的资产。如果剧情和结构写在同一个文件里， 每加一个结局都要动引擎，回归风险随内容量线性上升。

我的做法是把全部剧情节点、线索、结局外置为配置层， 引擎只认通用 schema，不引用任何具体节点 ID。 新增章节与结局只改配置，引擎零改动。

这不是自述——它可被验证。git 记录里 v1.6.4 的提交信息是：

v1.6.4: divergence x trap convergence (view-layer only, engine byte-identical)

新增了分歧与陷阱收敛的玩法，引擎层字节级零改动。 这句话能被 git diff 复核。

两个设计机制

线索门控

8 个选项带 requiresClue 条件。 玩家未掌握对应线索时，选项渲染为「未解锁」的幽灵按钮，并给出不剧透的暗示。

作用：把线索从「信息回现」升级为「路径解锁」， 让循环母题从一个设定变成能被玩到的机制。

跨轮记忆

结局揭示的线索持久化保存，重玩时在早期节点触发记忆回现文本。

作用：让玩家每一轮都比上一轮多知道一点， 把「重复」从惩罚变成进度——这是循环叙事能否成立的关键。

面试时会怎么讲这个项目

问：为什么要做内容与引擎解耦？
因为剧情是最高频变动的资产。把变动源隔离出去，扩展才不会引入回归。 证据是 v1.6.4 引擎字节级零改动——不是我说解耦了，是 git 说的。

问：18 个结局，怎么保证不重复、都可达？
靠测试。可达性校验会断言每个结局都有路径能到达， 配置完整性检查会在测试阶段暴露错误，而不是等玩家卡死。
